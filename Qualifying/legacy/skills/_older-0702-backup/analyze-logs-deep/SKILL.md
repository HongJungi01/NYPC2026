# /analyze-logs-deep — 스냅샷 코드 대조 심층 로그 분석

`/analyze-logs`(단순 분석)의 **확장 모드**: 같은 파이프라인(facts → 루브릭 md → 이동)에
**스냅샷 코드 대조 레이어**를 얹어, 로그의 각 핵심 행동에 대해 "왜 이 기능이 이렇게
작동했나"를 실제 코드로 규명한다. 정본 정책 = `Logs/LlmAnalyzer/POLICY.md` **§6 DEEP 모드**
(+§1~§5 공통 루브릭). 시작 전 반드시 읽는다.

## 인자
- 인자 없음 → `Logs/LlmAnalyzer/input/` 의 모든 `*.txt` 처리.
- `<id>` 지정 → 해당 파일만 처리 (analyze-logs와 동일).
- **대조 코드 지정** — 로그를 만든 코드를 호출 시 함께 첨부하면 그 코드를 기반으로 분석한다.
  다음 어느 형태든 동등하다:
  - `snap:<MMDDHHmm[a-z]?>` — submission/ 스냅 id (예: `snap:07020517d`).
  - `snap:<경로.cpp>` — 임의 .cpp 경로 (예: `snap:submission/hybrid.cpp`).
  - 호출 메시지에 **코드 파일 첨부 또는 경로 언급** — 인자와 동등하게 취급.
  - 지정 없음 → 기본 **HEAD** = `submission/` 의 `^[0-9]{8}[a-z]?\.cpp$` 중 타임스탬프 최신.
  - **한 호출 = 대조 코드 하나.** 배치의 로그들이 서로 다른 코드 산출물이면 나눠 호출한다.

## 절차

0. **정책·기반 로드**:
   - `Logs/LlmAnalyzer/POLICY.md` (§6 DEEP 모드 포함) — 루브릭·형식 정본.
   - `.claude/skills/analyze-logs/SKILL.md` — 공통 파이프라인 절차(§0~3). 아래는 델타만 기술.
   - `.claude/skills/reflect-analysis/SKILL.md` §3(분류 프레임·시간지평)·§5(코드지도) — 코드
     대조의 시작점. 라인 번호는 시작점일 뿐이므로 **반드시 Grep/Read로 재확인**.

1. **대조 코드 판정**: 첨부/`snap:` 인자 > HEAD 순. 파일 존재를 확인하고 **식별자**를 정한다
   — 스냅 id면 그대로(예: `07020517d`), 경로면 파일명 기준(예: `hybrid.cpp`).
   이 식별자가 md 헤더 마커에 들어간다.

2. **각 `<id>.txt` 처리** — analyze-logs 절차 2(a~d)를 그대로 수행하되, 분석 작성(2c)에
   다음을 추가:

   a. **코드 대조 레이어**: §4 루브릭으로 짚은 핵심 국면·finding마다 대조 코드의 담당
      부분을 Grep/Read로 확인하고, 본문 해당 대목에 코드 원인을 병기한다 —
      `관찰(턴·행동) → 담당 코드 유무(파일:라인) → 발동 조건·임계와 그 턴의 실제 값
      → 왜 그렇게 행동했나 → A/B/C/D 예비분류 + 시간지평(i/ii/iii)`.
      (A 의도·정상 / B 부재·우연 / C 의도·모호구현 / D 무의미 — reflect-analysis §3 프레임.)

   b. **DEEP 헤더 마커(필수)**: md 최상단 헤더 블록 첫 줄에
      `> 분석 모드: DEEP — 코드 <식별자> 대조` 를 넣는다 (식별자 = 절차 1의 스냅 id 또는 파일명).
      (reflect 단계가 `분석 모드: DEEP` 마커로 출처를 판정해 새 스냅샷 접미를 `d`로 정한다.)

   c. **말미 `[코드 원인표]`**: finding별 한 줄 —
      `t.. 관찰 → 코드사이트(:라인) → 발동조건 vs 당시값 → 예비분류(A/B/C/D)+시간지평 → 신뢰도`.
      기존 `[무의미/손해 오더]`·`[봇 반영 후보]` 목록은 그대로 유지(반영 후보는 코드사이트까지
      특정 가능해짐).

3. **요약 출력**: analyze-logs 요약 형식 + `대조코드=<식별자>` + 예비분류 분포(예: `C2건 B1건`).

## 주의 (캐버트 완화의 경계)
- **내부 기능명은 코드 인용으로 검증된 것만** 언급한다(POLICY §6). 코드를 확인하지 않은
  추측 명명은 단순 모드와 똑같이 금지 — "관찰상"으로만.
- 로그 행동이 대조 코드로 **설명되지 않으면**(게이트 조건과 모순 등) 다른 버전의
  산출물일 가능성 — 단정하지 말고 `⚠️ 플래그`(올바른 코드를 첨부/`snap:` 재지정하라고 제안).
- **진단까지만**: 봇 코드는 읽기만 한다. `submission/*.cpp` 수정 금지(반영은
  `/reflect-analysis` 또는 `/analyze-reflect-deep`).
- raw `.txt` 불변·멱등성·플래그 규칙은 analyze-logs와 동일.
