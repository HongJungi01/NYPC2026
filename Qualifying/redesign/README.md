# redesign/ — 새 봇 클린룸 재설계 작업 공간

기존 봇(`submission/07031406d.cpp` 계보)을 **처음부터 다시 설계**한다. 옛 코드는 손대지 않고
동결(§ `../legacy/`, `../submission/`)한 채, 여기서 **기능·매니저를 목적별로 다시 나눠** 새로 쌓는다.

## 재설계 접근 원칙 (현재까지 합의)

1. **깨끗한 시임은 그대로 재사용 후보**: 정확 시뮬레이터·전투수학·eval·경로·상대모델·I/O·롤아웃은
   이미 자유함수/구조체라 경계가 분명 — 재구현보다 이식·정제 대상.
2. **주 재모듈화 대상 = `gen_cmds` 모놀리스(~1150줄)**: Economy/Movement/Military 가 지역 람다와
   공유 가변상태(`budget`·`mobile`·`committed`·`a`)로 얽혀 있음. 이 **공유 가변 컨텍스트를 끊어
   책임을 분리**하는 것이 재설계의 핵심(구 "배분 재편"의 본질).
3. **정확성 우선**: 시뮬레이터는 referee와 byte-exact 유지가 전제. SIM_TEST/OBS_TEST 게이트를
   새 구조에서도 첫날부터 건다.
4. **아직 없던 것은 신설 여부 별도 판단**: Transposition Table, 진짜 토큰-인지 이터레이티브
   디프닝은 기존에 없었다(스텁). 새로 넣을지는 근거 확인 후.

## 개발 프로세스 정책 — 기능 단위 · 사용자 판정 (2026-07-06 확정)

재설계 **기능 제작 단계**는 다음 케이던스로 진행한다:

1. **기능 하나 = cpp 하나.** 기능을 구현할 때마다 그 기능만 담은 별도 cpp로 빌드한다(누적 모놀리스 아님).
2. **각 기능을 랜덤시드 10판으로 테스트**한다. 상대는 **`../simulator/sample-code.py` 로 고정**(공식 샘플봇).
3. **판정은 사용자가 직접** — 사용자가 그 10판 로그를 읽고 기능이 제대로 작동했는지 판별한다.
4. **기능 제작 과정에서 회귀/승률 등 자동평가 메커니즘을 (Claude가) 사용하지 않는다** —
   `abtest.ps1`/`crossplay.ps1` 승률로 기능 채택·기각·회귀판정을 내리지 말 것. 그 판단은 오직 사람이 로그로 한다.
   (정확성 게이트 = 컴파일 · SIM_TEST · OBS_TEST 결정론적 로그-동일성은 이 금지 대상이 아니며 §3대로 계속 유효.)

## 검증 인프라는 그대로 (완성 봇 단계에서 재사용)

위 기능 단위 사람-판정을 거쳐 **하나의 완성된 새 봇**이 나온 뒤에야, `../submission/` 의 스냅샷 풀 +
`abtest.ps1`/`crossplay.ps1` 로 **배틀 승률 검증**한다. 옛 스냅샷들이 다양한 상대 스파링 풀 역할을 한다.
(그 목적으로 `submission/` 을 동결 보존.) — 즉 승률 하니스는 *기능 제작 중*이 아니라 *완성 봇 단계*의 도구다.

> 튜닝 상수·과거 결정 이력은 `매니저_인벤토리.md` 와 `../legacy/policies/` 참고. 특히
> 레거시 풀 A/B 성적은 승패 평가 지표일 뿐 기능 결정 근거가 아니라는 원칙(구 submission POLICY §6)은
> 재설계에도 유효.
